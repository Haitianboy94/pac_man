# Pac-Man

A complete, playable recreation of the classic arcade game **Pac-Man**, built in Python with `pygame`, object-oriented design, and a modular, reusable architecture. Levels are generated by an external "A-Maze-ing" maze package assigned by another team, integrated through a custom adapter layer without modifying the third-party code.

## Description

This project reimplements the 1980 Namco classic: navigate a procedurally generated maze, eat pacgums, avoid four ghosts each with a distinct personality, grab power pellets to turn the tables and hunt the ghosts back, and clear at least ten levels of increasing challenge. The game features a full menu system, a persistent Top-10 highscore table, a pause menu, a cheat mode for reviewers, and clean error handling throughout — the game is designed to never crash on bad input, a failed maze generation, or an unexpected game state.

## Configuration

The game is configured via a JSON file passed as the single command-line argument. Standard JSON is extended to support `#`-prefixed comment lines, which are stripped before parsing.

| Key | Purpose |
|---|---|
| `highscore_filename` | Path to the JSON file used to persist the Top-10 highscore table |
| `level` | List of level numbers; its length determines the total number of levels in a full playthrough |
| `width`, `height` | Dimensions (in cells) of each generated maze |
| `lives` | Starting number of lives for the player |
| `pacgum` | Base pacgum count/identifier used by the maze layout |
| `points_per_pacgum` | Score awarded for eating a regular pacgum |
| `points_per_super_pacgum` | Score awarded for eating a super pacgum (power pellet) |
| `points_per_ghost` | Score awarded for eating an edible (scared) ghost |
| `seed` | Fixed seed used to generate the very first level, so level 1 is reproducible between runs; every level after that is generated with a random seed |
| `level_max_time` | Time limit, in seconds, for each level before it is forfeited |

Any missing or invalid key is clamped to a safe default, logged clearly, and the game continues — it never crashes on a malformed config file. Unknown keys are ignored.

## Highscore

Highscores are stored as a JSON file (path set by `highscore_filename` in the config) mapping player names to their best score. On load, the file is read into an internal min-heap capped at the ten highest scores — any new entry that pushes the table past ten entries evicts the lowest score. This keeps insertion and eviction efficient without needing to re-sort the whole list on every save.

Validation is enforced on every entry added, whether from disk or from a fresh game:

- Player names must be 1–10 characters, alphanumeric and spaces only
- Scores must be non-negative integers

If the highscore file is missing, corrupted, or contains invalid data, the game logs the problem and proceeds with an empty table rather than crashing — no run is ever blocked by a bad highscore file.

At the end of a game (win or lose), the player is prompted to enter their name on the Game Over / Victory screen; submitting saves the score and returns to the main menu, where the current Top-10 table is also viewable.

## Maze Generation

Per the project's constraints, this team does not implement its own maze generator. Instead, an externally assigned **A-Maze-ing** package (`MazeGenerator`) is used exactly as provided, with all integration handled by a loader/adapter in `src/maze_generator.py`.

### The adapter's responsibilities

- Translate this game's configuration (width, height, entry/exit, seed) into the vendor package's constructor arguments.
- Convert the vendor's raw `list[list[int]]` wall-bitmask output into this project's own `Dir` (`IntFlag`) representation, consumed by the maze/UI layer.
- Retry generation (with a randomized seed on subsequent attempts) if the vendor package fails to construct a maze or produces an unsolvable layout, since the vendor class has no built-in retry or validation of its own.
- Raise a project-specific `MazeGenerationError` only after all retries are exhausted, which the game scene catches to fall back to a small, hand-built, guaranteed-solvable maze — so a maze-generation failure degrades gracefully instead of crashing the game.

### Seeding rule

Per the level-progression requirement, the first level is always generated with the fixed `seed` from the configuration file (so level 1 is identical and testable on every run), while every subsequent level uses a randomly chosen seed.

### Bit scheme

Each maze cell is a 4-bit value describing which of its four walls are closed:

| Direction | Bit |
|---|---|
| North | 1 |
| East | 2 |
| South | 4 |
| West | 8 |

A set bit means that wall is present; a clear bit means the corridor is open in that direction. This scheme is shared end-to-end between the vendor package, the adapter, and this project's own `Maze`/`MazeWall` rendering classes.

## Implementation

### Core loop

`pac-man.py` parses the config file, opens the pygame window sized to fit the generated maze plus a UI border, and hands off control to a `Game` instance, which owns the display surface, the persistent `Config`, `GameState`, and `Highscore`, and drives the main loop: poll events → update the active scene → render → flip the display, capped at 60 FPS.

### Scenes

The game is organized around a small `Scene` state machine (`MainMenu`, `GameScene`, `GameOverScene`, plus an in-scene `PauseMenu`). Every scene holds a reference back to the owning `Game`, letting any scene request a transition (by setting `next_scene_id`) or read/write shared state such as the highscore table or the current level. `Game._create_scene` is a small factory that constructs the requested scene on transition.

### Player movement

The player moves continuously (not in instant per-cell jumps): a `move_progress` float tracks how far Pac-Man has traveled across the current cell, advanced every frame by `speed * dt`. Wall legality is checked before allowing movement to continue into an upcoming cell, and a buffered `target_direction` lets the player queue a turn slightly before reaching an intersection, for responsive-feeling controls. The same interpolation pattern is used to smoothly reposition the sprite between cells rather than snapping.

### Ghost AI

Each of the four ghosts moves with the same continuous, interpolated motion as the player, but chooses its direction using a breadth-first search over the maze graph — guaranteeing genuinely shortest-path navigation rather than a shortsighted greedy heuristic, which avoids ghosts getting stuck oscillating in pockets or dead ends. A direction is re-evaluated every time a ghost fully arrives at a new cell, so it's always chasing a fresh target rather than committing to a stale path.

Each ghost type targets differently, giving them distinct personalities:

- **Blinky** — chases the player's current cell directly.
- **Pinky** — targets a handful of cells ahead of the player's current facing direction, ambush-style.
- **Clyde** — chases normally from a distance, but flees toward a random cell when it gets close to the player, giving it a "shy" character.
- **Inky** — targets a randomized cell near the player's position, for less predictable pathing.

When a super pacgum is eaten, all ghosts become edible: their AI switches to fleeing toward whichever maze corner is farthest from the player, and their sprite swaps to a "scared" animation. Eating an edible ghost awards bonus points and sends it back to its spawn corner, frozen for a short respawn delay, after which it resumes normal behavior.

A `_greedy_direction` fallback (single-step, distance-based, and reluctant to reverse direction unless it's the only legal option) is used only in the rare case that BFS finds no path — e.g. the ghost is already standing on its target cell.

### Pacgums and scoring

Regular pacgums are placed in most open corridors; four super pacgums are placed at the maze's true corners. Eating either removes it and awards points per the configured values; eating all pacgums in a maze completes the level. Score is tracked on a persistent `GameState` object that carries over between levels and lives, and never decreases.

### Lives, game over, and victory

Colliding with a non-edible ghost triggers a short death-pause and animation before respawning the player at the maze's center and decrementing a life (unless the invincibility cheat is active). Reaching zero lives, or running out of the per-level timer, ends the game; clearing every configured level wins it. Either outcome transitions to a shared Game Over / Victory scene showing the final score and prompting for a name to save to the highscore table.

### Cheat mode

A dedicated in-game cheat menu (reachable from the pause menu) toggles flags stored on `GameState` and read by the relevant systems each frame:

- **Invincibility** — ghost collisions are ignored entirely.
- **Ghost Freeze** — ghosts stop moving (their sprite still updates, so edible/scared coloring stays accurate even while frozen).
- **Super Speed** — the player's movement speed is multiplied.
- **Skip Level** / **Extra Life** — immediate one-shot effects on `GameState`.

An on-screen `CheatsIndicator` widget reflects whichever cheats are currently active, so reviewers can always see the game's state at a glance.

### Sound

`src/sounds.py` centralizes lookups for the game's sound effects (chomping pacgums, eating a ghost, death, sirens, level start, etc.), sourced from the `sounds/` directory. Entities and scenes trigger playback through this module rather than loading audio files directly, keeping asset paths in one place.

## General Software Architecture

```
pac-man.py                 Entry point: parses config, opens the window, starts Game
pac-man.spec                PyInstaller spec for packaging a distributable build
config.json                  Default game configuration
highscore.json                 Persisted Top-10 highscore table
resources/, sprites/, sounds/    Sprite sheets and audio assets used by the graphics/sound layers
vendor/
  mazegenerator-*.whl        The assigned "A-Maze-ing" package, used as-is, unmodified
src/
  resources.py              Resolves asset paths so the game runs both from source and packaged
  sounds.py                  Central lookup for sound effects (death, eat gum, eat ghost, sirens, etc.)
  game.py                    Owns the main loop and scene transitions
  game_state.py               Cross-scene, cross-level runtime state (lives, points, cheats, timer)
  maze_generator.py            Adapter/loader around the vendor MazeGenerator package
  types.py                      Shared enums: Dir (wall bitflags), PacGumType, GhostType
  config/
    config.py                    Config dataclass + defaults
    config_parser.py              JSON-with-comments parsing and validation
    highscore.py                   Persistent Top-10 highscore table (min-heap backed)
  entities/
    entity.py                       Abstract base for anything with an image/rect and per-frame update
    player.py                        Pac-Man: continuous movement, input buffering, animations
    ghost.py                          Ghost AI: BFS pathfinding, per-type personalities, edible/eaten state
    maze.py                            Wraps the adapter's Dir grid into wall/pacgum sprites for rendering
    maze_wall.py                        Individual wall-segment sprite used by Maze
    pacgum.py                            Regular/super pacgum sprite, with the power-pellet blink animation
  scenes/
    scene.py                              Abstract base scene, holds a back-reference to Game
    scene_id.py                            Enum identifying each scene for transitions
    main_menu.py                            Title screen, highscores view, instructions view
    game_scene.py                            The core gameplay scene
    game_over.py                             Shared win/lose scene with name entry
  ui/
    button.py, text.py, panel.py              Base interactive/text/panel widgets
    game_ui.py                                  Composes the in-game HUD (clock, points, lives, level)
    game_clock.py, points_counter.py, lives_counter.py   Individual HUD widgets, each bound to GameState
    pause_menu.py                                Pause overlay: resume, cheats, return to main menu
    cheats_indicator.py                            HUD widget showing which cheats are currently active
  graphics/
    sprites.py, general_sprites.py, hud_sprites.py, text_sprites.py   Sprite-sheet lookups per asset category
    animation.py                                     Frame-timed animation helper shared by entities
    player_animations.py                               Pac-Man's per-direction/death animation state machine
tests/
  test_config_parser.py       Unit tests for config parsing/validation (not graded, per project guidelines)
  test_highscore.py            Unit tests for the highscore table's validation and top-10 eviction
```

Each layer only depends on the ones below it: `scenes` orchestrate `entities` and `ui`, `entities` depend on `maze`/`types` but not on scenes, and the maze adapter is the single, isolated boundary against the third-party package — nothing outside `maze_generator.py` ever touches the vendor `MazeGenerator` class directly. The vendor wheel itself lives untouched under `vendor/`, installed as a dependency rather than vendored into `src/`.
